## 🔬 Engineering Areas I've Worked On

Instead of repeating repositories that are already visible in my pinned section, this section highlights the **technical problems, concepts, and systems** I have worked with.

### 🤖 1. AI Agents & Workflow Orchestration

- Built and experimented with **50+ AI automation workflows**, spanning RAG pipelines, document-oriented tasks, email scheduling, and automated reporting.
- Explored multi-agent patterns with an **orchestrator and specialized agents** for tasks such as Excel, Word, and PowerPoint operations.
- Used **LiteLLM** to connect workflows to hosted language-model providers through a common interface.
- Explored **RabbitMQ** for message-based communication between agents and components.
- Worked with agent memory concepts and the boundary between planning, tool selection, and task execution.
- Focus on making workflows easier to reason about by separating agent responsibilities and validating actions before execution.

### 📈 2. LLM Evaluation & Observability

I have configured and tested AI observability tooling and explored how to connect quality signals with application and infrastructure telemetry.

| Layer | Tools / Concepts | Questions It Helps Answer |
|---|---|---|
| **Model quality** | Opik / Comet ML | Is the response relevant or correct? How do prompts and RAG context affect the result? What usage and cost signals are available? |
| **Application telemetry** | OpenTelemetry, Jaeger | Where did a request spend its time? Which operation failed? How do services and agent steps connect? |
| **Infrastructure metrics** | Prometheus, Grafana | What is happening to CPU, memory, throughput, queue depth, and error rates? |

Areas explored:

- Configuring Opik and testing trace logging from applications.
- Evaluating LLM responses, RAG context, prompt versions, and token-usage signals.
- Understanding the differences between **logs, metrics, traces, and model evaluations**.
- Designing a correlation approach so a model interaction can be connected to the application request and infrastructure conditions around it.
- Comparing cloud and self-hosted observability options, including local deployment workflows.

### 🧠 3. RAG, Retrieval & Memory Design

- Explored **Retrieval-Augmented Generation (RAG)** and the role of retrieval in grounding model responses.
- Worked with vector-search options such as **Qdrant and FAISS** and explored embedding-based retrieval.
- Investigated chunking, embedding choices, retrieval quality, and hybrid retrieval approaches.
- Compared vector-based approaches with ideas such as **Vectorless RAG** and structured knowledge formats.
- Explored agent memory as a design problem: what belongs in short-lived working state, what should be searchable, and when information should be retrieved.
- Interested in evaluating retrieved context rather than judging a generated answer in isolation.

## 🧠 Problem Solving & Computer Science Fundamentals

I practise DSA with an emphasis on **pattern recognition, invariants, state design, and deriving transitions** rather than memorizing isolated solutions.

- **Arrays & strings:** sorting, two pointers, sliding window, prefix sums, Kadane's algorithm, and rearrangement patterns.
- **Binary search:** boundary templates, binary search on the answer, and writing the feasibility predicate.
- **Trees & graphs:** traversal, Union-Find, lowest common ancestor, strongly connected components, and graph-based DP.
- **Dynamic programming:** state and transition derivation across arrays, strings, and graphs.
- **Competitive programming:** parsing multiple test cases, reading constraints carefully, and implementing robust C++ input/output.
- **SQL:** filtering, joins, aggregation, subqueries, and interview-style query practice.
- **System design:** API boundaries, data modelling, trade-offs, queues, observability, and component responsibilities.

My preferred question to ask while solving a problem is: **What property makes this pattern valid, and how can I prove it?**

## 🛠️ Engineering Principles I Care About

- **Validate before executing:** treat LLM output as a proposal, not automatically trusted instructions.
- **Observe the full path:** use evaluations, traces, logs, and metrics for the different questions they answer.
- **Keep responsibilities clear:** separate model reasoning, tool execution, APIs, storage, and infrastructure.
- **Protect sensitive information:** avoid exposing passwords, tokens, credentials, and private data in logs or prompts.
- **Understand the failure mode:** debug from evidence and assumptions rather than adding complexity too early.
- **Document trade-offs:** explain why a tool or architecture fits the constraints, not only which tool was used.
